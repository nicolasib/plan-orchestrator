Four things you stop doing.

Concurrency is the upgrade, not the point. Every line below is true at one lane.

Clearing context between phases

One OS process per task, each with its own session id. Every task starts on a fresh context, and nothing carries over except the commits.

$ claude -p task 3 · lane A $ claude -p task 5 · lane B $ claude -p task 4 · lane A

Sitting through the run

Nothing runs until you approve the lane plan. After that the plan goes to the end with nobody in the loop, and the CLI prints one line per task boundary.

lane A task 3 done 4 commits lane B task 5 done 2 commits lane A task 4 running

Paying for a dead session

A checkpoint is written before a task starts and again the moment it exits. Usage limits and API errors stop being restarts. Resume never reads a transcript.

$ plo resume --plan <plan.md>

Reviewing lane by lane

One review at the end, over the combined diff. Orphaned references after deletions, helpers two lanes each wrote, drifted types. A per-lane review structurally cannot see those.

$ plo integrate --plan <plan.md>

It does not guess.

Everything the graph needs is already written in the plan: the files a task declares it will write, and the interfaces it consumes and produces. plo parses that literally, then prints the graph and stops. Nothing touches disk until you approve it.

write-write
Two tasks declare the same path. They serialize into one lane. Hard.
interface
A Consumes or Produces block names another task by number. Hard.
semantic
Docs-only and no-writes heuristics. Soft, printed with its evidence.
override
A JSON file beside the plan, committed with the reason. Wins over everything.

Two details that matter in practice. A negation in the plan is honoured, so (new, do not touch b.test.js) records one write and not two. And reads are never conflicts: two tasks importing the same helper stay parallel.

The whole tool is five commands.

plo analyze

Prints the lanes, the edges and the evidence for each one. Read-only. This is the gate, and it is the cheap place to correct a wrong graph.

plo init

Writes the checkpoint from the lane plan you approved.

plo run

Creates the lane worktrees and executes. A lane that hits a limit dies alone.

plo integrate

Merge, then barrier tasks, then the full suite, then one cross-lane review. That order is not negotiable.

plo clean

Removes the worktrees. Refuses while a lane still has unmerged commits.

When a lane dies, git outranks the state file.

On resume, a task left running becomes interrupted, and a task with commits on its lane branch that the checkpoint calls unfinished is promoted to done. The other lanes never noticed. What stopped, and the report it wrote on the way out, sits on the dashboard next to the command that restarts it.

Where it is the wrong tool.

Parallelism buys wall clock, not budget

Three lanes spend tokens about three times as fast. If the goal is surviving a usage limit, the win is the checkpoint and the process isolation, and one lane already gives you both.

Under about six remaining tasks, skip it

Worktree and process setup costs more than the parallelism returns. Plain subagent-driven development is the better tool at that size.

The semantic layer is a heuristic

It is deliberately soft. It prints its reasoning, and a JSON file beside the plan overrides it. A missing edge is the expensive error, which is exactly why the gate exists.

Two commands and it is on your PATH.

Node and git are the whole dependency list. There is nothing to build.

bash 
$ git clone https://github.com/nicolasib/plan-orchestrator
$ cd plan-orchestrator && npm link

$ plo analyze --plan <plan.md> --max-lanes 3
  read the graph, correct it, then: plo init && plo run
